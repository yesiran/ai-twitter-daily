最近流传着一个建议：把你的 CLI 参数替换成单个 --json 载荷，这样 agent 就能更有效地使用你的工具。Agent 以结构化的方式思考。嵌套数据可以干净地映射到 JSON。扁平的参数会迫使人们采用别扭的约定。这是个合理的假设。

我们做了测试。构建了一个合成 CLI，跨嵌套服务包含 30+ 个值。在两种模式下跑了五个模型。参数在正确性上全胜：每个模型都是 5/5，包括测试中最小的那个。JSON 的正确性在较小的模型上下降了。Haiku 4.5 在 JSON 模式下 5 次部署只对了 2 次。

成本差距更大。JSON 模式在每个模型上的单任务成本高出 4x 到 11x。钱都花在了重试上。当 CLI 拒绝 JSON 时，agent 会读取错误、尝试修复、再试一次。JSON 有更多失败的方式，而每次失败都意味着更多输出 token。

Shell 转义税让情况更糟。agent 生成了正确的 JSON，却在 shell 转义上出了问题。不同的 shell 有不同的引号规则。在 PowerShell 上，参数和 JSON 之间的成本差距是 9x。在 Bash 上则缩小到 1.5x。同样的模型，同样的载荷。参数在两者上都很稳定：$0.05 vs $0.07。

更深层的发现：参数对输入空间的约束足够强，以至于即使较小的模型也能稳定地产出正确的输出。JSON 要求模型自己管理结构，而这是一种并非每个模型都付得起的能力税。

保留你的参数吧。
