9.5 · 前沿🔁 转发 @eliebakouch15:44 · ♥ 839 · ↺ 87
说白了，这是一个建立在闭源模型之上的闭源编排器。如果说以前你无法控制模型，现在你甚至无法控制使用的是哪些模型以及使用了多少。这根本不是 "AI sovereignty"

我也读了技术报告，对技术细节谈谈看法：

fugu（不是 ultra 版本）基本上是一个分类器，它在每轮对话中选择最有可能正确回答的模型（换句话说，就是一个 router）。与 opus 相比，这导致它在 SWE Bench pro 上低了 -10 分，在其他基准测试上有一些提升，但非常微弱。论据可能是它降低了成本，但没有相关信息，所以情况可能恰恰相反。他们还有一个自动研究基准测试，将其与前沿模型 "Model A, B and C" 进行对比，不公开对比的是哪些模型，这真的很疯狂。此外，这可能不支持开箱即用地添加新的 llm，因为你需要重新训练分类器

关于 fugu ultra，这基本上是一个高级规划模式和编排器，这个模型可以针对一个查询输出一个包含多个 "workflows" 的计划。我对 workflows 的理解是，它们会说："生成 model A 子智能体来实现这一目标，然后使用 model B 进行评判，最后用 model C 进行总结"，这其实就是一种 test time scaling 计算策略。我觉得这种方法还行，但它的局限性在于，他们需要在智能体开始工作之前预测好一切，这就是为什么他们将其限制在 5 步以内。在我看来，你需要根据在 t 时刻获得的信息来预测在 t+1 时刻要生成什么，而不是根据在 t=0 时刻获得的信息。还有其他问题，比如 fable 5 在 terminal bench 上的评分是错的，而且他们对于 LLM 池中包含哪些模型含糊其辞、很不明确（他们只提到了闭源 api 那个）

最大且最明显的问题是，他们引入了一种针对模型的 "best of N" 的 "test time scaling" 方法，但他们真的从未报告过实现某个基准测试/任务所需的输出 token 数量或成本

这里合理的对比对象不是单独的 opus，而是启用了 ultracode/workflows 的 opus，不是 kimi，而是 kimi swarm 等等……这次发布非常非常让人困惑

我对模型路由器（model routers）信心不足——我非常愿意改变我的想法，但这代表了我目前的看法

- 我认为不知道自己在使用什么模型并不是件好事。用 LLMs 编写代码是一项需要培养的技能，而对模型建立直觉是其中的一部分

- 大多数人目前还不具备这项技能，这就是为什么许多公司抱怨人们在用昂贵的方法处理愚蠢的事情。模型路由器承诺在用户无需做任何事情的情况下解决这个问题，但我认为问题在于缺少给用户的反馈闭环。我宁愿我们去研究如何帮助用户变得更聪明

- 考虑到 prompt cache 之类的事情，我甚至不知道你能进行多大程度的模型路由。能做的其实很有限

- 它们的有效性被某种影响着整个 AI 领域的动态给夸大了。如此多的公司在拼命寻找机会并尝试一切。模型路由是模型实验室唯一无法做的事情，所以每个人都蜂拥而上
💡指出模型路由器的三大硬伤：阻断了用户与特定模型交互的直觉反馈闭环、受限于 Prompt Cache（跨模型缓存失效导致成本上升）、且多为非模型厂商在焦虑下的跟风产物。这提示产品经理不要迷信“无感智能路由”，应保留用户对模型的控制感知，并重点解决跨模型路由导致的 Prompt 缓存失效与延迟问题。
