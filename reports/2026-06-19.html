隆重推出 AA-Briefcase，面向下一代智能体知识工作（agentic knowledge work）的基准测试

AA-Briefcase 是我们全新的基准测试，用于在行业专家构建的复杂项目中，测试模型处理长周期知识工作任务的能力。模型将在为期数周的项目中接受评估，每个项目都包含许多相互关联的任务以及数千个输入源文件。

我们在 @AnthropicAI 的 Claude Fable 5 下架前对其进行了评估，它目前以 1587 的 Elo 评分领跑，紧随其后的是 Claude Opus 4.8 (max, 1356)、Opus 4.7，以及 @Zai_org 最近发布的 GLM 5.2 (max, 1266)。

运行每个 AA-Briefcase 任务，Claude Fable 5 平均花费 $31，其次是 Claude Opus 4.8（$10.40）、GPT-5.5 (xhigh)（$3.68）和 GLM-5.2 (max)（$2.40）。

AA-Briefcase 包含四个私有场景，每个场景代表一个设置在真实组织背景下的多周知识工作项目。第五个公开场景已通过 @huggingface 发布，用于展示场景结构、提交和评分（AA-Briefcase Lite）。这不计入 AA-Briefcase 的官方结果，仅作演示之用。

AA-Briefcase 的核心要素：

➤ 真实的长周期项目：AA-Briefcase 超越了单一、孤立的提示词，通过在一个连贯的长周期项目中评估模型。任务逐周推进，依托共享的机构背景，并需要交付诸如财务模型、董事会汇报 PPT 和设计原型等成果。

➤ 海量碎片化的上下文：AA-Briefcase 要求模型在数千个输入中进行推理，包括公司文档、会议纪要、大规模数据导出、25,000+ 条 Slack 消息和 3,500+ 封电子邮件。这些来源碎片化、杂乱无章，且往往包含符合现实的矛盾，测试模型能否应对现实世界知识工作中的模糊性。

➤ 综合评分标准与两两对比评分：AA-Briefcase 将针对客观真实准确性的二分类标准检查，与针对分析质量和展示质量的两两对比评分相结合。与许多仅关注单一指标的评估不同，AA-Briefcase 更全面地测试了智能体能力，揭示了模型虽然生成了看似精美但实际上错误或缺乏分析严谨性的输出的情况。

➤ 由行业专家构建：AA-Briefcase 的场景镜像了现实世界的知识工作，其任务由来自 Google、McKinsey & Company 和 BCG 等公司的数位数据科学、产品管理和企业战略专家历时数月开发而成。任务挑战源自专业经验，使 AA-Briefcase 能够更好地反映定义现实世界知识工作的模糊性、杂乱的上下文和相互冲突的优先级。

主要结果：

➤ Claude Fable 5 以 1587 Elo 领跑 AA-Briefcase：紧随其后的是 Claude Opus 4.8 (1356)，而表现最好的非 Anthropic 模型 GLM-5.2 (max) 则以 1266 分落后约 90 分。请注意，Claude Fable 5 在 AA-Briefcase 的任何任务中都没有使用 Opus 4.8 备用方案。

➤ 在测试的模型中，每个任务的成本差异高达约 800x：Claude Fable 5 领跑该基准测试，但平均每个任务的成本超过 $31，相比之下，DeepSeek V4 Flash (max) 仅需约 ~$0.04。性价比最高的选择是开源权重模型，如 GLM-5.2 (max) 和 DeepSeek V4 Pro (max)，其中 GLM-5.2 (max) 的评分仅比 Claude Opus 4.8 (max) 低约 90 Elo，而成本不足其 25%。

➤ 现实世界的复杂性对模型来说依然困难：表现最好的 Claude Fable 5 仅在 3% 的 AA-Briefcase 任务中满足了所有评分标准。在 91 个任务中的 31 个任务中，没有一个模型在评分标准上的得分超过 50%。

➤ 任务难度随所需输入文件数量的增加而呈比例上升：对于每次评分标准检查，我们都会确定通过所需的源文件集。在所有模型中，随着文件数量的增加，通过率都会下降，尽管顶尖模型的衰减程度低于较弱的模型。

💡增量：针对长周期Agent任务的新基准AA-Briefcase发布，揭示最强模型（Claude Fable 5）在复杂企业任务中的完全通过率仅为3%，且单次任务成本高达31美元，而开源的GLM-5.2 (max)以25%的成本达到了Opus 4.8约93%的性能。意味着：复杂Agent产品的核心瓶颈仍在多源长上下文处理，当前阶段企业级Agent架构应优先考虑GLM-5.2/DeepSeek V4等高性价比开源模型作为平替，以平衡极高的API调用成本。

如果你正在努力打造一家涉及 web app 的十亿美元级公司，这里有我关于前端架构的一些笔记。

如果你不这样做，可能也没什么大问题，但总有一天你会雇人来修复它，而如果你在第 1 天就做一些关键的优化，那个人其实可以去做其他更有价值的事情。

你甚至不需要学任何东西，反正你也会让你的 agents 去做！

好，内容如下：
- 让你的服务端代码生成 openapi 规范，然后再生成所有相关的客户端代码。千万不要手动做这个。手动编写后端类型而不是生成它们应该被禁止。

- 你需要决定客户端如何与后端通信。rest/graphql 都可以，如果是这样，请直接使用 tanstack query。其他库看起来差不多，但 tanstack query 确实是神级的（goated）。

- 如果你想要 linear 风格的同步设置或离线模式，在第 1 天就要对此进行深入思考并进行架构设计。后期再补上这个太繁琐了。

- 人们喜欢使用原生的 react router，但从那以后情况已经好多了。试试他们的新框架模式，或者甚至直接使用 tanstack router。使用 route data loaders。

- 如果你在 query params 中存储了大量状态，请将其作为一等公民，并确保其类型安全。使用 nuqs 或 tanstack query。

- 大多数应用只需要一个针对服务端状态的单一状态管理方案，这就足够了。如果你有其他定制需求，我挺喜欢 zustand 和 xstate/store。

- 如果你有一个超级互动的应用，其中各种元素在视图中移入移出，有大量的前端状态需要维护，背景音乐在播放等等，静下心来学习 xstate。相信我，如果你想保持理智，你需要将你的前端建模为一个状态机，否则你将深陷 useEffect 地狱。

- 朋友们，React compiler 已经来了，useMemo 和 useCallback 的时代已经过去。相应地更新你的认知吧。

- Tailwind 简单又好玩，但很难维护一个具有一致样式的庞大应用。你需要一个 "agent-first design system/component library"，但也许这是改天的吐槽话题了。

- 不要害怕修改你的路由库以更贴合你的需求。很多应用都有 "drawers" 来显示额外信息。你 100% 应该能够说“这是一个路由，把它变成一个 drawer”，然后所有事情都应该从那里处理。

- 使用 isPending 和 isError 来管理加载和错误状态简直是疯狂。多用用 Suspense 和 ErrorBoundary。

- 如果你正在构建任何与 AI 相关的项目，我认为在第 1 天就为 websockets 和 SSE 确定一条黄金路径，长期来看会带来丰厚的回报。

- 如果你正在构建一个 SPA，不要使用 next.js。这字面上毫无道理。你为什么要这么做？

- 绝对要部署在 Cloudflare 或 vercel 上。虽然还有其他服务，但相信我，它们有一些奇怪的缺失功能。

- 假设你做出了人们想要的东西，下一步工作就是建造工厂，以便高效地生产这个东西。采取相应的行动。
💡增量：提出AI时代Web应用需在首日确立WebSocket/SSE黄金路径，并呼吁构建“Agent优先的设计系统/组件库”以应对高频异步交互。意味着：AI应用的前端正从静态展示转向高动态流式交互，产品负责人需推动研发采用状态机（XState）和流式架构，为未来Agent直接操控UI预留接口。
