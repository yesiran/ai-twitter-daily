以下是在 Codex 中为 GPT-5.6 Sol 启用 1M token 上下文窗口的方法。

尽管我们已经在性能和成本方面把 Codex 的上下文限制调优到了最佳状态，但这是一个常见需求，所以在此将其记录下来。

更大的上下文窗口让 Codex 能在总结旧内容之前保留更多代码、工具输出和对话历史。你需要一个支持它的模型。例如，GPT-5.6 Sol 有文档记载的 1,050,000 token 窗口。

打开 ~/.codex/config.toml，并在顶层、任何 [section] 标题之前添加或更新这些设置：

```
model = "gpt-5.6-sol"
model_context_window = 1000000
model_auto_compact_token_limit = 900000
```

第一个设置选择模型。第二个告诉 Codex 使用 100 万 token 的上下文预算。第三个在约 900,000 token 时启动自动历史压缩，留出一些余量。保存后重启 Codex 客户端并开始新会话。

要在不更改默认设置的情况下，为单个 CLI 会话试用此配置：

```
codex -m gpt-5.6-sol \
-c model_context_window=1000000 \
-c model_auto_compact_token_limit=900000
```

玩得开心，但也请知道我们精心调优了默认设置！
💡实质增量：Codex 可通过 config.toml 手动解锁 GPT-5.6 Sol 的 1M 上下文（文档标称 1,050,000 token），并给出 auto-compact 900k 的推荐阈值。信号：OpenAI 默认上下文刻意保守（成本/性能权衡），长上下文是可选项而非默认——做 agent 产品的要自己在「原始长窗 vs 压缩」之间算经济账。

“监控”作为 AI 安全通用解决方案的失败之处：

监控和所有其他软件一样，运行在不稳定且难免宕机的基础设施上，总会有一定的停机时间。监控的一次短暂失灵会不会打开潘多拉魔盒？人们会接受在所有系统上都采用 fail closed 的监控吗？

监控会产生误报。人们厌倦了阅读虚假的或无关紧要的问题，就不再去看了。监控疲劳是真实存在的问题，而“解决所有精确率与召回率的问题”和其他任何难题一样困难

这些都是平淡无奇的失败。更离奇的失败包括模型与其监控器串通等等

监控绝不是完美的万灵药。除非真正对齐模型，否则任何方法最终都行不通

我不喜欢这种状况。我希望事情并非如此。如果这些问题上能有一场充分知情的公开辩论会更好。说清楚一点，你仍然可以跟上动态；有公开活动、播客、论文、Substacks 等等。大多数有趣的想法都在外面被讨论和辩论，只是大多在小众论坛里。
